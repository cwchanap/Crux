# HPA-396 Frozen IDM Stem Pilot Design

**Status:** Proposed  
**Date:** 2026-08-20  
**Linear:** HPA-396 — Evaluate frozen Inverse Drum Machine on fixed drum-stem benchmark pilot

## Decision summary

Implement Inverse Drum Machine (IDM) as the third **benchmark-only** transcription backend over the fixed HPA-328 HTDemucs pilot population.

The shape remains intentionally small:

1. pin official `bernardo-torres/inverse-drum-machine` at commit `456656868538205ef756912c7cf5b0fd936de8af` and model `idm-44-train-kits`;
2. run IDM in one isolated Python 3.11 `uv` environment behind the existing persistent `WorkerProcess`;
3. **do not import `idm.inference`** in the worker: load the exact SHA-verified `model.yaml` and checkpoint directly with `OmegaConf` + `hydra.utils.instantiate()` + strict `load_state_dict()`;
4. use the model encoder's native onset/velocity activations plus the pinned decoder sigmoid/`PeakPicking` evaluation path, with no manual onset override and no required synthesis/masking output;
5. extend the existing closed backend descriptor, prediction-v2, taxonomy, mapping, metadata-policy, and zero-hit tables for exactly one third backend family;
6. consume the immutable HPA-328 handoff and its retained HTDemucs input/OaF prediction artifacts; never rerun HTDemucs or OaF;
7. rebuild both cohorts with unchanged HPA-325 `score_cohort()` / `write_cohort_reports()` and pair only identical source/input hashes through public `published_comparison` helpers;
8. keep full-mix IDM work to a separately named five-song smoke whose membership is generated by a tested pure selector from the real HPA-328 population before any IDM inference;
9. stop before scored execution if the pinned runtime/model/WAV/PeakPicking contract cannot be reproduced.

Do **not** add prediction v3, a plugin/registry system, a generic runner framework, a second scorer, required reconstructed IDM stems, score-driven tuning, full-corpus IDM execution, production API integration, training, fine-tuning, or manual event correction.

## Current dependency reality

The HPA-328 implementation is merged, but its production experiment is not. The merged PR records an operational hold: Task 11 was not run, no production separator locks were generated, and no native separator inference/handoff was produced.

Consequences:

- offline HPA-396 implementation/tests may proceed;
- real HPA-396 stem/full-mix execution remains blocked until a production `crux.oaf-separation-pilot/v1` handoff exists;
- concrete smoke IDs cannot be truthfully named in this planning PR;
- test-fixture IDs and MuScriptor smoke IDs `1..5` must never be substituted for the production population.

The selector algorithm is frozen now. `scripts/freeze_idm_smoke.py` computes and commits the five actual production IDs immediately when the production handoff exists and **before any IDM HPA-328/full-mix inference**.

### Peak-picking provenance

The frozen validation peak parameters do **not** come from `model.yaml`'s configured training `peak_picking` value. They come from `Decoder.__init__`, which always creates:

```python
self.peak_picking_val = PeakPicking()
```

Therefore the pinned defaults are:

```text
div_max = 20
div_avg = 10
div_wait = 16
div_thre = 5
normalize = false
```

The worker always passes `activation_rate=` explicitly to `peak_picking_val`. The fallback path is not used.

`PeakPicking` itself calls `librosa.util.peak_pick()` and `librosa.samples_to_time()`. Therefore the isolated `uv.lock` pinning the upstream-compatible librosa 0.9.x line is part of **peak-picking reproducibility**, even though the WAV loader deliberately does not use librosa. A move to librosa 0.10+ would be a new runtime identity and requires review.

## Why `idm.inference.load_model()` is not the benchmark load boundary

The pinned `idm/inference.py` executes at import time:

```python
rootutils.setup_root(__file__, indicator=".project-root", pythonpath=True)
ROOT_PATH = Path(rootutils.find_root())
```

and `load_model()` then rewrites:

```python
log_dir = ROOT_PATH / log_dir
```

before discovering the checkpoint with `find_checkpoint(...)`.

That is unsuitable for the isolated installed package because:

- `.project-root` is not installed with the `idm` package;
- caller-supplied `model_root` cannot become authoritative;
- checkpoint selection uses recursive discovery despite HPA-396 already freezing exact paths/hashes.

The worker therefore bypasses only this discovery wrapper while keeping the same actual model construction performed by upstream when `model.yaml` exists:

```python
config_path = model_root / "checkpoints" / "model.yaml"
checkpoint_path = model_root / "checkpoints" / "val-epoch=518-global_step=0.ckpt"

# host verifies exact bytes/hashes before worker startup
cfg = OmegaConf.load(config_path)
model = hydra.utils.instantiate(cfg)
ckpt = torch.load(checkpoint_path, map_location="cpu")
model.load_state_dict(ckpt.get("state_dict", ckpt), strict=True)
model = model.to(device).eval()
```

No checkpoint glob, fallback config path, rootutils project discovery, or friendly-name resolver remains in the scored path.

## Native velocity is diagnostic-only

Upstream defines:

```python
max_value * sigmoid(x) ** log(exponent) + threshold
```

with `max_value=2`, `exponent=10`, `threshold=1e-7`, so the expected raw model band is:

```text
[0.0000001, 2.0000001]
```

Crux's six-decimal quantizer intentionally canonicalizes very small positive values to `Decimal(0)`. Therefore `"0"` is a valid persisted diagnostic representation and must not invalidate a song.

Rules:

1. worker/backend raw decode requires `native_velocity` to be finite; it does **not** reject the precise expected model band;
2. snapshot diagnostics count `native_velocity_out_of_expected_band_count` using the original raw float and the exact `[1e-7, 2.0000001]` expectation;
3. persistence quantizes at the normal six-decimal artifact boundary, so tiny valid values may become `"0"`;
4. prediction-v2 metadata accepts canonical finite decimal strings in the structural envelope `0 <= value <= 2.000001`, including `"0"`;
5. `velocity_midi = round(clamp(raw_native_velocity / 2.0, 0.0, 1.0) * 127)` remains diagnostic only;
6. no velocity value participates in peak selection, HPA-325 matching, or F1.

The narrow structural envelope protects the persisted metadata contract without turning expected floating-point/quantization behavior into population loss.

Host conversion example:

```python
NativeEvent(
    time_sec=1.25,
    native_class_id="KD",
    model_output_bin=4,
    native_midi_note=None,
    native_metadata={
        "frame_index": "215",
        "native_velocity": "1.337421",
    },
    confidence=0.83,
    velocity_midi=85,
)
```

### Metadata policy table widening

Today `NATIVE_METADATA_SCHEMAS` stores exact allowed-value sets. IDM has unbounded structured strings, so HPA-396 explicitly widens the **value policy type**, while keeping the schema/key table closed:

```python
MetadataValuePolicy = frozenset[str | None] | Callable[[str | None], bool]

NATIVE_METADATA_SCHEMAS = {
    OAF_METADATA_SCHEMA: {
        "upstream_8hit_group_id": OAF_GROUP_IDS | {None},

    MUSCRIPTOR_METADATA_SCHEMA: {

        "native_velocity": _valid_idm_native_velocity,
```

`_validate_metadata()` uses membership for fixed sets and the predicate for IDM values. This is one small closed-table extension, not a metadata plugin framework.

### Remove the proven mapping duplicate before adding IDM

`map_muscriptor_prediction()` and `map_oaf_prediction()` already duplicate the same descriptor checks, mapped/unmapped bookkeeping, and `MappedPredictionEvent` construction. HPA-396 makes that a three-copy pattern, so first extract:

```python
def _map_prediction(
    prediction: NativePrediction,
    prediction_map: PredictionMap,
    key_of: Callable[[NativeEvent], str],

```

```python
def map_muscriptor_prediction(...):
    return _map_prediction(prediction, prediction_map, lambda e: str(e.native_midi_note))

        prediction,
        prediction_map,
```

A mismatch is fatal. Re-reading external manifests in the comparison stage would add no stronger evidence than the already-frozen run/report hashes.

## Five-song full-mix smoke

Smoke membership selection is code, not hand-executed prose.

Create one pure selector:

```python
@dataclass(frozen=True)
class IdmSmokeCandidate:
    simfile_id: int
    source_duration_sec: Decimal
    common_reference_event_count: int

@dataclass(frozen=True)
class IdmSmokeCase:
    reason: Literal["short", "long", "sparse", "dense", "median_duration"]
    simfile_id: int


def select_idm_smoke_cases(
    candidates: Sequence[IdmSmokeCandidate],
) -> tuple[IdmSmokeCase, ...]: ...
```

Candidate population:

- real production HPA-328 handoff member;
- HTDemucs input status success/resumed;
- reference mapping loads successfully;
- only pre-IDM duration/reference-event evidence is used.

Select **without replacement** in this exact order:

1. `short`: minimum `(source_duration_sec, simfile_id)`;
2. `long`: maximum duration; equal duration chooses lowest `simfile_id`;
3. `sparse`: minimum `(common_reference_event_count, simfile_id)` among remaining rows;
4. `dense`: maximum event count; equal count chooses lowest `simfile_id` among remaining rows;
5. `median_duration`: compute the median duration over the **remaining pool after the first four selections** using ordinary numeric median (even counts use the arithmetic mean of the two middle durations), then choose minimum `(abs(duration - median), duration, simfile_id)`.

Unit tests pin duration ties, event-count ties, selection without replacement, and odd/even median parity.

`scripts/freeze_idm_smoke.py` loads the real handoff/reference evidence, calls only this selector, and writes canonical:

```text
runtime/idm/smoke.json
schema = crux.idm-smoke/v1
```

The generated file is shape/lineage-validated and committed before any IDM request over the production HPA-328 population. No F1/model output participates.

Full-mix smoke source resolution lives in a separate `IdmFullMixSmokeRequest` with `source_cache_dir`; it never leaks into the primary stem request or headline comparison.

## Risks / hard gates

- **Production HPA-328 handoff absent:** offline code may proceed; real smoke/pilot execution cannot. Do not fabricate membership.
- **Installed `idm.inference` path:** forbidden as model loader; direct verified config/checkpoint construction is the frozen path.
- **PeakPicking compatibility:** Task 0 executes the exact pinned sigmoid + `peak_picking_val(..., activation_rate=...)` path and asserts the defaults frozen into the lock.
- **librosa drift:** WAV decode uses soundfile, but upstream PeakPicking still depends on librosa; runtime-lock drift changes benchmark identity.
- **Timeout-dependent population:** 1800-second request timeout is frozen before scores and hashed into inference identity.
- **Zero-hit artifacts:** mandatory IDM zero-hit map entry is tested before runner work.
- **Diagnostic velocity:** valid tiny values may persist as `"0"`; expected-band diagnostics cannot invalidate valid upstream onset artifacts.
- **Metadata recovery:** frame index and pre-MIDI native velocity are persisted before real inference.
- **Training-data provenance:** record StemGMD provenance/licensing context for HPA-329; the pinned repository/weight license itself is no longer treated as unspecified.

## Acceptance criteria

HPA-396 is complete when:

1. the exact pinned isolated runtime resolves without patching upstream semantics;
2. Task 0 directly loads SHA-verified model config/checkpoint without `idm.inference` discovery and asserts every model/PeakPicking/velocity parameter later frozen in the lock;
3. the exact canonical WAV tensor path is proven with no conversion/resampling;
4. runtime/model/license identities are frozen before score inspection;
5. prediction-v2 supports IDM while OaF/MuScriptor bytes/invariants remain unchanged;
6. zero-hit IDM artifacts score successfully;
7. frame index/native velocity are persisted, including valid quantized `"0"` velocity;
8. real HPA-328 handoff/reference/timing/input/OaF artifacts are hash-bound with no rerun or discovery;
9. every fixed row has a valid IDM prediction or explicit native failure code;
10. both cohorts use unchanged HPA-325 scoring;
11. OaF↔IDM pairing requires identical source/input hashes and matching recorded reference/timing/taxonomy/scoring identity;
12. smoke membership is generated by the tested selector and committed before real IDM inference;
13. full-mix smoke remains separate;
14. runtime/class coverage/failure/license/provenance evidence is reported;
15. no result-driven tuning, training, full-corpus expansion, or production registration occurs.
